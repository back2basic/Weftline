# Shared-board create experiment — UNWIRED, not an enforcement boundary

`createSharedTask` is a local dependency-injected experiment, not a route and not an Appwrite adapter. It creates only a ready task. It passes the opaque session and the exact board ID to a trusted lookup, checks the returned membership and board ID, and sends an explicit four-field row and team-read-only permission to a trusted writer. It rejects caller-supplied extra fields, including identity and permissions. Fake-dependency tests do not prove actual authentication, membership, permissions, or storage behavior.

## Required real boundary before any integration

- The server-side lookup must validate the actual current session with the identity provider, establish the user from that session, check active membership for the exact board, and obtain the board's authoritative team ID. It must not trust client-supplied identity or membership. The team must contain exactly the board's intended readers; role changes and removal must have verified effects on existing rows. A membership result is only as trustworthy as this implementation.
- The privileged writer must target a dedicated, explicitly selected database and table, not one selected by a request. Its explicit schema must accept `boardId`, `title`, `status`, and `createdBy` with appropriate required types and limits. It must apply exactly the supplied team-read permission and no user write, update or delete permission; no implicit defaults or broader table-level reads may override this policy.
- Provision and independently verify row security and table permissions: no direct client create, update, delete, or permission changes; no broad table-level read. Do not reuse the current personal-task table, whose client permissions do not establish this policy. Attempt direct API bypass, ACL escalation and outsider creation against disposable resources before any exposure. The fake writer in this repository does not enforce these settings.
- Resolve the **membership-revocation race** before enabling: a membership lookup can succeed, then revocation can commit before the privileged write. This helper cannot prevent that interleaving. A supported, independently tested authorization/write serialization or equivalent mechanism must define and enforce effective revocation, including both orderings and session revocation. Another pre-write lookup alone is not atomic.
- Test the real adapter, session and cookie handling, direct API bypass resistance, ACL semantics, concurrent membership changes, failures and ambiguous write outcomes against the supported server version. Review the exact integration and retain the existing fail-closed server routes until all gates are met. The local fake tests are not authorization to enable or deploy.
