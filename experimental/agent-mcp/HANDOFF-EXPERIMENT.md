# Experimental task–knowledge handoff convention

This is an optional client convention, **not a server-enforced attachment**. It adds no task fields or review records. A candidate ID proves neither existence, ownership, association, authorization, current state nor that a worker or reviewer followed this protocol. By default the tool is off and the existing tool list is unchanged. To opt in, supply `--enable-handoff --handoff-namespace NAMESPACE` together, in that order, alongside independently configured task and knowledge groups. The namespace is a nonsecret deployment-unique identifier for the task backend: all cooperating clients for the same task backend must configure the same namespace; distinct task backends sharing a knowledge store must use distinct namespaces. Allocation and consistency are operator responsibilities, not enforced by the tool. Do not use secrets or private data as the namespace.

The namespace is explicitly validated and snapshotted at process startup, never inferred from board or tool input. Missing, duplicate, standalone or invalid namespace or duplicate enable flag rejects startup. `handoff_candidates` takes only `task` and `claimGeneration`; board and namespace are fixed by validated startup configuration. The result is local, read-only and does not contact the listener or authorize access. An actor can derive IDs without the tool; do not treat its output as an access decision.

## Portable encoding and bounds

`experimental/agent-mcp/handoff-id.js` exports `deriveHandoffIds(namespace, board, task, claimGeneration)`. Namespace, board and task are ASCII identifiers matching `^[A-Za-z0-9][A-Za-z0-9._-]{0,35}$` (1–36 bytes); generation is an integer 0–999999 inclusive. Inputs outside those bounds are rejected, never normalized. For instructions encode `["weftline-handoff-v1","instructions",namespace,board,task]`; for a deliverable encode `["weftline-handoff-v1","deliverable",namespace,board,task,claimGeneration]`. The version marker and type are domain separators. Canonical JSON has no whitespace, ASCII literal strings in that order, and generation in shortest unsigned decimal representation; UTF-8 encode it, SHA-256 those bytes, lowercase hex encode, and take the first 32 hex characters. Prefix `i` or `d` respectively. IDs are 33 ASCII bytes. No NUL, newline, BOM or trailing bytes are included.

An arbitrary preexisting document may occupy a candidate ID, and the truncated hash can collide. Neither an occupant nor the ID/hash proves a link, ownership, or authorization; both remain untrusted. If an ID is already occupied, stop and independently investigate; never adopt or overwrite it merely because it matches the candidate. The namespace is not an access-control boundary or a provider receipt.

**Upgrade and reconfiguration:** this version changes the old unnamespaced experimental IDs; existing clients or documents do not migrate automatically. Changing the namespace also changes both IDs, causing cooperating clients with mismatched settings to derive different candidates. Coordinate an offline inventory and explicit reconciliation/migration with all clients before switching; preserve old records and unresolved intents, do not silently fall back to old IDs, and do not infer a relationship from either ID. This candidate has not been deployed.

## Human, worker and reviewer procedure

1. Before task genesis, select a unique task ID and derive its instruction ID (the generation argument does not affect that ID). Create the instruction document at that ID, confirm the exact creation receipt, retain its content and acknowledge its exact intent. Agree out of band to use **knowledge generation 0**, and independently read that exact version to confirm the intended instructions. Only then use the existing supported guarded genesis path. The instruction document is data, not executable code; assess it as untrusted content. A create is not proof of its current head or immutable access.
2. Worker: independently perform existing eligibility, authorization and hold checks. Derive the instruction candidate, read exactly generation 0 using `knowledge_read_version`, and assess it; a missing, denied, malformed or uncertain read is not permission to proceed. A read is historical, not a snapshot or proof that no hold appeared afterward. Claim using the existing guarded operation. Establish the **claimed task successor generation**, not the pre-claim task generation; use that successor as `claimGeneration` for the deliverable ID. Obtain it from independently assessed task history and a matching claim receipt; if uncertain, stop and reconcile. Despite the parameter name, it identifies the relevant claimed-state generation, including one produced by a rejection.
3. Worker: create the deliverable candidate as knowledge generation 0, compare the confirmed receipt to the intended operation, and acknowledge with the entire original exact intent. Confirm/read generation 0 as appropriate, then use existing guarded submit. Preserve the original intent securely. A knowledge acknowledgment is not approval and cannot replace the task guard.
4. Reviewer: perform existing eligibility, authorization, hold, role and self-review checks. Independently establish the relevant claimed generation from task history, derive the candidate, read exactly knowledge generation 0 and assess its content as data before existing guarded approve or reject. In the review-v1 transition protocol, rejection returns the task directly to **claimed**, retaining the claimant and advancing its generation; it does not require or allow a fresh claim of that already-claimed version. Before resubmitting, the worker establishes that claimed successor generation, derives a fresh deliverable ID from it, creates and acknowledges the revised document, then submits the claimed version. For example, claim produces generation 1, submit produces review 2, and rejection produces claimed 3; the two deliverable IDs use 1 and 3. Observations are advisory and non-snapshot: do not assume the most recent visible historical entry is current.

Separate knowledge and task writes are **not atomic**: failures can leave instruction or deliverable orphans, tasks without confirmed documents, or ambiguous results. Review-v1 itself has no held state or hold transition: any hold checks required by a deployment are external to this protocol and are not enforced by this handoff. A hold, role or eligibility change can race checks or a separate document write. On unknown outcomes retain journals and original intents, use the existing exact-receipt reconciliation procedures, and do not automatically retry writes or infer failure from a missing receipt. Legacy clients and other privileged writers can bypass this convention; enforcement would need a separately designed protocol. Provider credentials, row ACLs, transaction behavior, size limits, deployed ingress, cross-process journal coordination and revocation must be verified independently for the real environment. The synthetic tests are not evidence of real provider authorization. See `KNOWLEDGE-WRITE-EXPERIMENT.md` and `WRITE-EXPERIMENT.md` for the actual flags, acknowledgment, recovery and limitations.
