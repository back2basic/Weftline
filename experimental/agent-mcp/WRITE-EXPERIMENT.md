# Local opt-in claim/submit experiment

The existing server remains read-only with its existing arguments. For this experimental local-only mode, append these arguments in this order: `--enable-writes --journal /absolute/private/directory --backend-endpoint <provider-endpoint> --backend-project <project> --backend-database <database> --backend-table <table>`. The separately started local TLS review listener must explicitly set `WEFTLINE_REVIEW_AGENT_SCOPED_WRITES=1`; proxy and read-only listener modes reject that option. Each mutation and receipt request uses a separate scoped route, which compares all four journal values against the immutable configuration used to construct that listener's store before invoking the authenticated review service. An older, unenabled or mismatched listener cannot handle these scoped requests and the adapter retains an unknown pending intent. This is not a separate discovery/preflight, and the comparison runs on the same receiving request as the operation. The listener and TLS trust remain trusted: a malicious server or trusted CA able to impersonate it can forge results; other legacy routes and separately running writers are not fenced. The journal also binds its marker to the exact scope strings and fails closed on a mismatch. The directory must already exist, belong to the process user, have mode 0700, and reside on a trusted local filesystem with trusted parent directories. Never share a journal between unrelated actors, boards, listeners, or environments. Nothing selects a journal automatically. Remote HTTPS mode is not supported for writes.

The added `claim` and `submit` tools take `operation`, `task`, `guardGeneration`, and `taskGeneration`; actor and board come only from validated startup configuration. The journal persists the exact intent before dispatch. A pending intent blocks new work across restarts and processes. `reconcile` accepts `currentGuardGeneration`, independently established by the operator; the original generation remains bound to the saved receipt. Only an exact matching positive receipt clears the pending state. A negative, denial, timeout, disconnect or missing receipt remains unknown: do not retry a mutation. A historical receipt does not prove the task still exists or remains current. Stale locks and damaged records require manual offline investigation, not deletion or automatic recovery.

Discovery and resolution use the startup `--guard` even in write mode. A successful claim or submit advances the guard, so those reads will fail closed until the server is restarted with an independently established current guard. A receipt is historical and does not independently establish the current guard. Write and reconcile tools accept their own explicit generation; supplying it is not authorization and the receiver checks the actual session and guard. Losing both journal marker and record is indistinguishable from a fresh directory; independent durable inventory is needed to detect that loss.

This is experimental, not production authorization. The runtime, local journal and filesystem, HTTPS listener, CA, response path and provider must be trusted. Journal records contain task and actor identifiers; secure the directory and backups. The listener's non-atomic authorization/read and trusted-writer limitations still apply; this does not establish Appwrite conflict behavior, real-provider permissions, crash/failover guarantees, cross-host coordination or atomic revocation. No live session, deployment or registration is implied.
