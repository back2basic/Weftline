# Experimental knowledge-write intent journal

This local, single-host component is used by the experimental knowledge-write MCP adapter; the journal itself makes no network calls. It does not establish provider idempotency, authorization, current document state, or transaction outcomes.

`createKnowledgeWriteJournal(absoluteDirectory, scope, actor)` takes an existing owner-owned `0700` directory. `scope` has exactly `endpoint`, `project`, `database`, `table`, `boardId`, `teamId`; the operator/integration must bind these to the **actual** backend and receiver, not an arbitrary label. `actor` must be the authenticated receiver actor. The directory, its ancestors, the runtime and same-user processes are trusted against replacement or modification. Files are owner-owned `0600`, regular, single-link and opened without following their final symlink; no claim is made against hostile ancestor replacement, root or same-user tampering. Use a filesystem that actually honors exclusive creation, rename and fsync; network filesystems and restored snapshots have not been validated.

An intent has exactly `operation` (`create` or `edit`), `operationId` (32 lowercase hexadecimal characters), `documentId`, `previousGeneration` (-1 for create), `title`, and `html`. No session or key is accepted. Title is nonblank and at most 200 UTF-8 bytes, HTML at most 1024 UTF-8 bytes, and the serialized intent at most 4096 bytes. These are local bounds, not a claim about the provider's serialized row capacity. Integration must verify the actual provider payload capacity separately.

* `begin(intent)` durably reserves the operation ID and saves the complete private intent before returning `pending`; only after that return may the integration dispatch the exact request. A pending, unknown, or reconciled-but-unacknowledged operation blocks another write. The intent, including title and HTML, is stored **in plaintext at rest**; protect the directory, its backups and recovered snapshots accordingly.
* `inspect()` returns only `empty`, `pending`, `reconciled`, `acknowledged`, `unknown`, or `blocked`. Missing state or a missing current reservation is unknown, never empty. Malformed or unsafe storage throws; errors leave the lock and need offline investigation.
* `recoverPending()` is for the **trusted runtime only**. It returns `{status:'pending', intent}` or `{status:'reconciled', intent}` with a fresh exact saved snapshot only when the bound marker, corresponding state and reservation validate; otherwise it returns generic `unknown` or `blocked`. It does not accept or return a session or key. Never expose its result or payload in MCP tool results, protocol errors, logs, or other untrusted outputs. It is not an authorization check: the integration must independently establish the authenticated actor and actual receiver scope before using it. Errors can leave a lock for offline investigation. Recovery neither dispatches nor retries a write and does not establish its remote outcome.
* `confirm(intent, result)` accepts only a Buffer of at most 256 bytes containing strict UTF-8 JSON with exactly `{"status":"confirmed"}` (duplicate keys are rejected) and only when every supplied intent field equals the saved pending intent. It assumes that result came from a **separately trusted receiver** that authenticated the actor and checked the exact request against its actual backend. This API does not authenticate the result or create a receipt; an arbitrary caller can forge confirmation. Never call it on a generic HTTP success, timeout, error, or non-exact result. Unknown remains pending; confirmation retains the exact intent and blocks another begin until explicit acknowledgment. There is no retry or cancel API.
* `acknowledge(intent)` compares all six original fields inside the lock and durably transitions the matching reconciled operation to `acknowledged`; repeating the same exact intent is idempotent while that record remains current. A different or old intent cannot acknowledge a pending or different operation. Equality outcomes can act as an oracle at the trusted local boundary, not as server authentication; lost original content requires offline recovery. Once the next intent starts, the old acknowledgement is no longer repeatable.

## Crash and recovery boundary

The lock is an exclusively created directory. It is never reclaimed automatically, including after an exception or process death; offline recovery requires stopping all users, preserving and inspecting all files, and determining the outcome independently. Durable ID reservation precedes state replacement, each file is fsynced, and relevant directory updates are fsynced. A crash before state persistence can burn an ID or leave a lock; a crash after state persistence can leave pending even if no dispatch occurred. A crash after dispatch or during confirmation leaves an indeterminate remote outcome unless the trusted receiver can confirm the exact request. Never infer non-dispatch from an absent receipt or retry automatically. A failed fsync/rename is uncertain and leaves the lock; do not clean up temporary files on error.

Reservations are retained indefinitely to prevent reuse inside this one intact journal. Deleting an older reservation, rolling back a snapshot, copying or independently initializing another journal, or losing the whole directory can defeat that property; there is no independent inventory or tamper-proof monotonic counter. Loss of both marker and state cannot be distinguished from first use. Storage exhaustion and unbounded reservations require operational planning, not automatic deletion. Stale-lock recovery is an offline operator responsibility; tests do not simulate power loss or validate a specific filesystem's durability.
